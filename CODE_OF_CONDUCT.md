# 🤝 Code of Conduct

## Sindhi AI Keyboard

> **Built for the community. Respectful to everyone. Focused on creating technology that serves people.**

Sindhi AI Keyboard is being developed as a long-term community-focused technology project.

As the project grows, it may involve developers, designers, language experts, researchers, security professionals, accessibility advocates, domain experts, translators, testers, and community members from around the world.

This Code of Conduct establishes the standards for respectful and constructive participation.

---

# 🎯 Purpose

The purpose of this Code of Conduct is to create a project environment where people can:

- 🤝 Collaborate respectfully
- 💡 Share ideas
- 🐛 Report problems
- 🧪 Test software
- 🌐 Improve Sindhi language technology
- 📚 Improve documentation
- 🧑‍💻 Contribute technical work
- 🎨 Improve design and accessibility
- 🔐 Discuss security responsibly
- 🌾 Share real community needs
- 🔌 Help shape the future Sindhi SDK
- 🌍 Support Sindhi communities worldwide

Participation should be based on respect, good faith, and constructive collaboration.

---

# 🌍 Our Standards

Participants are expected to:

### 🤝 Be Respectful

Treat other people with dignity and respect regardless of:

- Technical experience
- Geographic location
- Language
- Background
- Professional status
- Contribution size
- Role within the project

A beginner asking a question deserves the same basic respect as an experienced developer.

---

### 💬 Communicate Constructively

When disagreeing:

- Explain your reasoning.
- Focus on the idea rather than the person.
- Provide evidence where possible.
- Suggest alternatives.
- Remain open to correction.

Healthy disagreement improves software.

Personal attacks do not.

---

### 🧠 Assume Good Faith

Mistakes happen.

A contributor may:

- Make a coding mistake.
- Misunderstand documentation.
- Submit an incomplete contribution.
- Report something incorrectly.
- Use the wrong terminology.

Start with clarification rather than hostility.

---

### 🌐 Respect Language Contributions

Sindhi language technology depends on people with different linguistic knowledge.

Contributors may have different:

- Dialects
- Writing styles
- Terminology preferences
- Technical backgrounds
- Regional experiences

Language disagreements should be handled through evidence, linguistic reasoning, community context, and respectful discussion.

---

### 📚 Respect Cultural Context

Sindhi AI Keyboard is intended to serve Sindhi communities worldwide.

Contributors should approach cultural, literary, linguistic, and historical material responsibly.

Cultural differences should be discussed respectfully rather than used to attack other participants.

---

# 🚫 Unacceptable Behavior

The following behavior is not acceptable within project spaces.

## Harassment

Examples include:

- Personal insults
- Threats
- Intimidation
- Repeated unwanted contact
- Deliberate humiliation
- Targeted hostility
- Sexual harassment
- Hate-based harassment

---

## 🗣️ Personal Attacks

Technical disagreement is allowed.

Personal attacks are not.

Do not attack someone because you disagree with:

- Their implementation
- Their technical opinion
- Their feature proposal
- Their language suggestion
- Their design
- Their architecture proposal

Critique the work, not the person.

---

## 🚨 Threats

Threats of violence, harm, retaliation, or intimidation are prohibited.

---

## 🔐 Privacy Violations

Do not publish or distribute another person's private information without appropriate permission.

This includes:

- Private addresses
- Private contact information
- Passwords
- API keys
- Authentication tokens
- Private conversations
- Private documents
- Confidential information

---

## 🕵️ Unauthorized Access

Do not attempt to access:

- Private repositories
- Accounts
- Servers
- Databases
- APIs
- Infrastructure
- User data

without authorization.

Security research must follow the project's security disclosure process.

See:

```text
SECURITY.md
````

---

## 🦠 Malicious Contributions

Do not intentionally submit code or resources designed to:

* Steal data
* Compromise devices
* Capture keystrokes
* Bypass security
* Introduce malware
* Circumvent authentication
* Damage infrastructure
* Abuse user information

---

# ⌨️ Special Responsibility for a Keyboard Project

A keyboard is fundamentally different from many ordinary applications because users may type highly sensitive information through it.

Therefore, contributors must treat keyboard-related functionality with particular care.

Do not intentionally introduce mechanisms that:

* Collect user keystrokes without authorization.
* Secretly transmit typed content.
* Circumvent privacy controls.
* Capture sensitive information.
* Disable user privacy protections.
* Add hidden telemetry without appropriate authorization and documentation.

Security and privacy are core project principles.

---

# 📡 Offline-First Respect

The project is intended to serve users who may have poor or unreliable internet connectivity.

Contributors should avoid introducing unnecessary requirements that make core keyboard functionality dependent on an internet connection.

When proposing a network-dependent feature, explain:

* Why network access is required.
* What happens offline.
* What data is transmitted.
* How the user experience behaves without connectivity.
* Whether an offline alternative is possible.

---

# 🚫 Ad-Free Principle

Sindhi AI Keyboard is designed to remain **ad-free**.

Contributors must not introduce advertising mechanisms into the core keyboard without an explicitly documented project decision.

This includes:

* Advertising SDKs
* Intrusive promotional screens
* Advertising banners
* Forced advertisements
* Ads appearing during typing

The project may eventually have sustainable commercial services, but advertising should not compromise the core keyboard experience.

---

# 🧠 Responsible AI

AI-generated output can be incorrect.

Contributors working on AI functionality should consider:

* Accuracy
* Reliability
* Privacy
* Security
* Bias
* Resource consumption
* Uncertainty
* User expectations

AI systems should not intentionally present uncertain information as guaranteed fact.

This is particularly important for specialized Skill Packs involving areas such as:

* 🌾 Agriculture
* 🏥 Healthcare
* ⚖️ Legal information
* 💰 Financial information
* 🏛️ Government services

Where appropriate, the application should communicate limitations and encourage professional verification.

---

# 📦 Skill Pack Responsibility

Skill Packs are modular capabilities designed for different user needs.

Contributors should ensure that Skill Packs:

* Do not unnecessarily interfere with typing.
* Do not secretly collect user information.
* Respect project privacy requirements.
* Respect device limitations.
* Clearly communicate important dependencies.
* Avoid unnecessary network requirements.
* Do not compromise the stability of the core keyboard.

---

# 🧪 Quality & Testing

Contributors should make a reasonable effort to test their work.

Before submitting a contribution:

* Test the affected functionality.
* Check for regressions.
* Consider low-end devices where relevant.
* Test offline behavior where applicable.
* Check language rendering.
* Check keyboard responsiveness.
* Document known limitations.

A contribution does not need to be perfect, but contributors should be honest about what has and has not been tested.

---

# 📝 Documentation

Important functionality should be documented.

Contributors should avoid intentionally introducing undocumented behavior that affects:

* Privacy
* Security
* Data processing
* Network access
* AI behavior
* Keyboard behavior
* User permissions
* Licensing

Documentation is part of the product.

---

# ⚖️ Licensing & Intellectual Property

Contributors must have the right to submit the material they contribute.

Do not submit:

* Copyrighted material without permission.
* Proprietary code without authorization.
* Confidential company information.
* Private datasets without appropriate rights.
* Third-party assets without compatible licensing.

Third-party licenses must be respected.

---

# 🌐 Language & Cultural Resources

Contributors working with Sindhi language data should respect the applicable:

* Copyright
* Dataset licenses
* Attribution requirements
* Terms of use
* Cultural context

Language resources must not be copied from restricted sources simply because they are accessible online.

---

# 🧑‍💻 Contribution Quality

The project values:

* Correctness
* Simplicity
* Maintainability
* Security
* Performance
* Accessibility
* Documentation
* Long-term sustainability

A larger contribution is not automatically a better contribution.

A small change that solves a real problem may be more valuable than a large feature that increases unnecessary complexity.

---

# 💬 Discussions

Project discussions should remain focused on improving the project.

Good discussion:

> "This approach may increase memory usage on low-end devices. Could we benchmark both options?"

Bad discussion:

> "Anyone who chooses this approach doesn't understand development."

Challenge ideas with evidence rather than attacking people.

---

# 🧑‍🏫 Beginners Are Welcome

The project should eventually be accessible to contributors at different experience levels.

Beginner contributions may include:

* Documentation fixes
* Translation improvements
* Typo corrections
* Testing
* Accessibility feedback
* Reproduction steps
* Small bug fixes
* Examples

Questions are welcome.

Nobody should be mocked for not knowing something.

# 🔒 Private Development Phase

During the current private development phase:

* The repository is private.
* External contributions are not currently accepted.
* Repository access is restricted.
* Project governance remains owner-controlled.

This Code of Conduct establishes the standards that will apply as appropriate when broader participation becomes available.

---

# 🚨 Reporting Violations

If public community participation is enabled and you experience or witness behavior that violates this Code of Conduct, report it through the project's designated official channel.

Do not publicly expose sensitive information while reporting an incident.

The project will provide the appropriate reporting contact when public community participation begins.

---

# 🔐 Security Reports Are Different

Do not use ordinary community channels to report security vulnerabilities.

Security vulnerabilities should be reported according to:

```text
SECURITY.md
```

This separation protects users and allows security issues to be handled responsibly.

---

# 🧑‍⚖️ Enforcement

Project maintainers may take appropriate action when this Code of Conduct is violated.

Possible actions may include:

1. 🗣️ Private warning
2. 📝 Formal warning
3. ⏸️ Temporary restriction
4. 🚫 Removal from a discussion
5. 🔒 Temporary loss of project access
6. ❌ Permanent removal from project participation

The response will depend on:

* Severity
* Context
* Intent
* Previous behavior
* Impact on others
* Risk to the project

Serious threats or malicious activity may result in immediate action.

---

# 🛡️ Protection Against Retaliation

People should not be punished for making a good-faith report of misconduct.

Retaliation against someone for:

* Reporting abuse
* Reporting harassment
* Raising a security concern
* Providing constructive criticism
* Participating in an investigation

is unacceptable.

False accusations made intentionally and maliciously may themselves be subject to review.

---

# ⚖️ Fair Enforcement

Enforcement should be:

* Proportionate
* Consistent
* Respectful
* Documented where appropriate
* Focused on protecting the community

Maintainers should avoid unnecessary public disclosure of private incident details.
